# Shrinking Giants and Faithful Bugs
*August 04, 2026*

Today, someone says they're running an eighty-billion-parameter model in four point three gigabytes of RAM on a Mac — and a thirty-five-billion-parameter model on an iPhone. Meanwhile, an AI system successfully migrated a pile of legacy COBOL to Java, and faithfully carried every single bug across with it. And Mexico's largest university has to make fifty-eight thousand students retake an entrance exam, because the AI that watched them take it didn't work. It's Tuesday, August fourth. This is TechCast Daily.

## Let's start with the number that's going to get quoted out of context all week. A Show HN post claims an eighty-billion-parameter Qwen model running in four point three gigabytes of RAM on a Mac, and a thirty-five-billion-parameter model running on an iPhone. Sitting right next to it on the front page is AirLLM, doing seventy-billion-parameter inference on a single four-gigabyte GPU. If your instinct is that the arithmetic doesn't work, your instinct is correct — and the reason it doesn't work is the actually interesting part.

There are three different numbers hiding behind the phrase model size, and the industry has gotten very comfortable letting them blur together. There's total parameters, which is the marketing number. There's active parameters, which is how much compute you actually spend per token. And there's resident memory, which is how much you have to keep loaded at any given instant. For a dense model, those three numbers move together, and an eighty-billion-parameter model really does need something like forty gigabytes even after aggressive quantization. But modern Qwen models in this class are mixture-of-experts. Eighty billion total parameters, roughly three billion active on any given token. The router picks a handful of experts, and the rest of that eighty billion just sits there being irrelevant for this particular word. So if you're clever about what stays resident and what gets paged in, the working set is enormously smaller than the headline. That's not a trick. That's the entire architectural point of mixture-of-experts, and it's why sparse models have quietly taken over the open-weight world. AirLLM attacks the same problem from a different angle, and it's worth understanding because the tradeoff is much starker. It does layer-by-layer streaming: load one transformer layer's weights into GPU memory, run the computation, throw the weights away, load the next layer. Your peak memory becomes the size of your largest single layer instead of the whole model. It genuinely works. But you have just converted a memory problem into a bandwidth problem, and bandwidth is not free. For every single token you generate, you are reading the entire model off disk or out of system RAM. Tens of gigabytes of traffic per token. It will run. It will not be pleasant. This is the distinction I'd hold onto: fits and usable are different claims, and the demos that go viral are always demonstrating the first one. Meanwhile, two other posts today are about what usable actually costs. One is a writeup on running Kimi and GLM — the strong open-weight Chinese models — at real production scale, where the constraint isn't whether the model is smart enough anymore, it's serving economics. And the other is a developer arguing for writing your own inference engines in C and C++ rather than shipping a Python stack. That sounds like masochism until you've tried to deploy a PyTorch dependency tree onto a customer's machine. You want a single binary, predictable memory, no runtime surprises, and latency you can actually reason about. Generic runtimes are built for research flexibility, and you pay for flexibility you're not using.

So the frontier moved. For about three years the interesting question was how many parameters you could train. Now the interesting question is memory hierarchy — what's resident, what streams, what's sparse enough to skip. That's not a machine learning problem. That's systems engineering, the kind people were doing in the nineteen nineties, and it's where the gains are right now.

## Next, a cluster of stories that are really one argument. Someone asked the question directly on Hacker News: what's the largest software project AI can complete entirely on its own? And on the same front page, sitting there like a punchline, is a report on an AI system that migrated legacy COBOL programs to Java — bugs included.

Start with the COBOL story, because it's the cleanest natural experiment we've gotten in a while. Somebody pointed a model at decades-old COBOL and asked for Java. It produced Java. The Java behaved identically to the COBOL, which means it also reproduced the bugs — the off-by-ones, the weird rounding, the special-case branch someone added in nineteen ninety-four for a customer who no longer exists. Now, here's the thing. By the stated success criterion, that's a pass. Behavioral equivalence is exactly what you ask for in a migration, because the alternative is a system that's subtly different in ways nobody can enumerate. Any human team doing this would also preserve the bugs, and would be right to. What the story actually reveals is that translation is not modernization, and organizations keep buying the first while budgeting for the second. The bugs were never the problem. The problem was that nobody understood the system, and you still don't — now you don't understand it in Java. So back to the original question: what's the biggest project AI can finish alone? I'd argue lines of code is the wrong unit entirely. The real limit is how much has to stay coherent at once, and how precisely the target is specified. A ten-thousand-line project with a crisp spec, a test suite, and clean module boundaries is far more tractable than a two-thousand-line change that requires knowing why a particular field is nullable. Models are extremely good at problems that are large but shallow. They fall apart on problems that are small but deep. Which brings us to the AI productivity gap, which was also on the front page today, and which is the most under-discussed story in this whole space. Individual developers report enormous speedups. Organizations report... not much. Both things are true simultaneously, and the gap isn't measurement error. It's that writing code was rarely the bottleneck. The bottleneck is deciding what to build, reviewing it, integrating it, and owning it in production at two in the morning. Accelerate one stage of a pipeline and you just relocate the constraint downstream. And the last piece of this: a post arguing you should prevent cognitive debt by manually retyping LLM-generated code. My honest take — the ritual is silly, the underlying observation is not. Retyping is not magic, and treating it as magic is cargo cult. But the observation behind it is real: if you accept code you don't understand, you've borrowed against your future self, and the interest comes due during an incident. Retyping happens to force comprehension by brute force. So do cheaper things. Write the test first. Explain the diff to a colleague. Review it as if a stranger wrote it, because functionally, one did.

The through-line here is that the fast part got faster and the slow part didn't. Everything downstream of code generation — comprehension, review, ownership — is still running at human speed, and no amount of tokens per second changes that.

## Speaking of things AI has made cheap to produce and expensive to consume: there's a post today titled, simply, SQLite critical CVEs — or LLM slop? That question mark is doing a lot of work, and the answer matters more than it sounds like it should.

You need one piece of context to evaluate this. SQLite is one of the most rigorously tested pieces of software that exists. The project maintains something on the order of a hundred times more test code than actual source code, with full branch coverage, fuzzing, and a test methodology borrowed from avionics. It is not an unaudited weekend project. So when a stream of critical-severity CVEs suddenly appears against it, base rates should immediately make you suspicious. Not because SQLite is bug-free — nothing is — but because critical, remotely-exploitable findings in that codebase should be rare and hard-won, not routine. What's actually happening across open source right now is a flood of AI-generated vulnerability reports, and the economics are brutally asymmetric. Generating a plausible-looking security report costs a few cents and thirty seconds. Triaging one costs a maintainer an hour of concentration and a spike of adrenaline, because you cannot safely ignore something labeled critical. The curl project has been extremely vocal about this — they've described the volume of AI-generated nonsense as a denial-of-service attack on maintainer attention, and they aren't being dramatic. There's a second-order effect that's worse. CVE severity ratings are already inflated, and now they're inflating faster. Every organization that gates deploys on scanner output is now getting paged about things that aren't real, which trains everyone to ignore the scanner, which means the one genuine critical gets ignored too. That's the actual security cost — not the bad reports themselves, but the calibration damage. And then, on the same front page, the other side of the coin: a Show HN for Nightcrawler, a local AI pentesting agent that runs on a smartphone. Same underlying technology, and I think a much better application of it, for a specific reason — it runs locally. Nothing leaves the device. Automated discovery is genuinely valuable when a human owns the output, the scope is authorized, and the findings get validated before anyone files anything. The difference between a useful security tool and slop generation isn't the model. It's whether there's a person on the hook for what comes out the other end.

The rule I'd extract: any system that makes it cheaper to make a claim than to check one will eventually drown in false claims. Security reporting just hit that threshold. Bug bounty programs are going to have to start charging for submissions, and I don't think anybody's going to like it.

## Now, the business of agents — and a set of stories that are all circling the same question from different directions. There's a Launch HN today for Hoplite, a Y Combinator company deploying coding agents in the cloud. Separately, AWS is letting the vibe-coding startup Superblocks embed directly into customer private clouds. A Marc Benioff-backed startup called June just raised twenty million dollars pre-seed. And Palantir's CEO, fresh off a billion-dollar profit quarter, called the AI industry Marxist.

Hoplite's pitch is concrete, which I appreciate. During onboarding they port your local setup into the cloud — sessions, memories, MCP servers — so your agents run somewhere with real compute instead of eating your laptop. But the interesting part is their stated thesis about where this goes. They think that within six to twelve months, developers will review dramatically less code and will instead review product output: does this new user flow work, does the page look right, does the API return what it should, does the CLI still run on Windows. And you'd be doing that while a hundred agents run concurrently. I think the first half of that is directionally right and the second half is where it gets hard. Review moving up the stack is real — we've watched abstraction levels rise for sixty years and this is the next one. But notice what it doesn't solve. Reviewing a hundred agents' product output is still a serial human looking at things one at a time, and visual verification is slower per unit than reading a diff, not faster. The bottleneck doesn't vanish; it relocates and changes shape. Whoever solves the aggregation problem — telling you which nine of a hundred results actually need your eyes — captures most of the value here. The AWS and Superblocks arrangement is a quieter story with bigger implications. Superblocks can now be embedded inside an AWS customer's own private cloud. Read that as: enterprises want these tools inside their perimeter, with their data never crossing a boundary, and the platforms are rearranging themselves to allow it. It's another step toward decoupling the application layer from any specific model. June, meanwhile, raised twenty million pre-seed on the premise that AI can solve the AI deployment problem — which is either elegantly recursive or a sign that the deployment problem is bad enough that people will fund anything pointed at it. Probably both. And then Karp at Palantir, who delivered a billion dollars of profit and then went on television to call the AI industry Marxist. Strip out the rhetoric, because the rhetoric is the product. The actual claim underneath is that frontier labs are too untrustworthy to be handed enterprise data. That is transparently self-serving — Palantir sells the alternative. It's also, annoyingly, pointing at something real, and it's the same thing the AWS story is pointing at. The unresolved question in enterprise AI isn't capability. It's who holds the data, who holds the liability, and where the perimeter sits.

Four stories, one axis. Every serious fight in enterprise AI right now is about location — where the model runs, whose network it runs in, and who's on the hook when it's wrong. The capability arguments are mostly settled. The custody arguments haven't started.

## Two stories now where AI met the real world and the consequences weren't a bad pull request. First: nearly a hundred and sixty thousand people took the entrance exam for UNAM, Mexico's largest university, entirely remotely — lockdown browser, AI-powered webcam proctoring, administered over several weeks. It went badly enough that fifty-eight thousand of them now have to take it again.

The tell was in the score distribution, and it's stark. Between twenty twenty-one and twenty twenty-five, about three and a half percent of test takers scored a hundred or better out of a hundred and twenty questions. This year, sixteen point three percent did. That's not grade inflation or a lucky cohort. A near five-fold jump at the top of the distribution means the measurement broke. Now, the interesting failure here is not that the AI proctor was bad at its job, though clearly it was. The interesting failure is architectural. In a physical exam hall, integrity rests on a stack of overlapping controls — a room, invigilators, seating arrangements, phones collected at the door, and the plain social friction of cheating with people watching. Every one of those is independently weak, and together they're strong. The remote setup replaced that entire stack with two things: a browser lockdown and a webcam model. Single point of failure, and when it failed, nothing else was there to catch it. Then there's the human cost, which is the part I keep coming back to. Fifty-eight thousand people have to retake this. Included in that number are students who studied for a year, sat the exam honestly, did brilliantly, and are now being told their result doesn't count — because the institution has no way to distinguish them from the people who gamed it. There was no per-candidate evidence trail good enough to separate the two populations, so everyone gets collectively re-tested. That's what it looks like when you deploy a system with no fallback and no forensics. The second story: Ukrainian drone operators have been destroying Russian armored vehicles, and even helicopters in midair, using four-hundred-dollar Shrike FPV drones. Starting in mid-July, those drones are shipping with autonomy hardware from the American company Auterion, and the plan is fifty thousand of these kits in the coming months. Here's how it works, and the detail matters. A human operator flies the drone into the area manually and designates a target up to half a mile out. Then they flip a switch, and the drone handles terminal guidance on its own — tracking and homing without further input. The reason this exists is not that anybody wanted an autonomous weapon for its own sake. It's jamming. The final seconds of an FPV attack are exactly when electronic warfare severs the video link, and a drone that has already locked its target doesn't care whether the radio still works.

Both stories are the same lesson at very different stakes. Autonomy narrows a system's tolerance for failure, and the question is never whether the model is accurate — it's what happens in the case where it isn't. Ukraine's answer is that a human designates the target and autonomy covers the last thirty seconds. UNAM's answer was that there was no answer, and fifty-eight thousand people are paying for it.

## Quick turn to the database world, which had a genuinely notable personnel move today. Andy Pavlo is joining ClickHouse to establish ClickHouse Labs.

If that name doesn't land for you, some context. Pavlo is the database professor at Carnegie Mellon, and for the past decade has been the closest thing this field has to a public conscience — the free database courses that a large fraction of working engineers have actually watched, and the annual year-in-review retrospectives that everyone reads and a few vendors dread, because they name names about which claims held up. Pavlo also founded OtterTune, an automatic database tuning company that shut down a couple of years back, which is worth remembering as a data point about how hard it is to sell database optimization as a standalone product. So the move is a signal, and I read it two ways. One, gravity in analytical databases keeps consolidating toward the columnar engines, and ClickHouse is buying credibility along with talent. Two, the pattern of academic database researchers landing at vendors rather than staying independent is now well established, and it means the neutral commentary layer for this field is getting thinner. Related, and much less glamorous: a post today on massively parallel Postgres backups. This is the kind of thing that gets six points on Hacker News and determines whether your company survives a bad Tuesday. Everyone specifies a recovery time objective in a document. Almost nobody has measured how long a full restore actually takes at their current data volume, and the answer is usually much worse than the document says, because backup speed was fine when the database was two hundred gigabytes and nobody re-measured at four terabytes. Parallelizing that work is unglamorous and it directly buys down the worst hour of your year.

Storage and retrieval remain where the real engineering is, and where the real money is. Every generation rediscovers this after a detour through something more exciting.

## Last one, and it's for the frontend people, though the idea generalizes. A project called Octane launched today with the tagline: React's programming model, compiled. And separately, Jane Street's UI library Bonsai got attention. These two are closer relatives than they look.

The premise behind Octane is one the React team itself conceded years ago with the React compiler. Hooks are a genuinely excellent authoring model — you describe your interface as a function of state, and you stop thinking about mutation. Hooks are also a fairly expensive runtime model, because the framework has to re-run your component and diff a virtual tree to figure out what actually changed. You're paying at runtime, on every user's device, to compute something that was largely knowable when you built the app. So compile it away. Keep the ergonomics developers like, and emit fine-grained updates that touch precisely the DOM nodes that changed, with no reconciler in the loop. Now, Svelte and Solid have been making exactly this argument for years, and they were right, and they said so loudly. What's changed is the framing. React's programming model is now being treated as a specification that multiple implementations can target, rather than as an inseparable bundle with React's runtime. That's a meaningful shift — it means the mental model developers have already paid to learn becomes portable, and the runtime becomes an implementation detail you can swap. Bonsai is the same insight arriving from a completely different intellectual tradition. It's Jane Street's UI library, written in OCaml, and it's built on incremental computation — a dependency graph where changing an input recomputes only what actually depends on it, and nothing else. They've been running this in production on serious financial software for years. It's the fine-grained reactivity idea, derived from first principles by people who needed provable performance and had a type system strong enough to enforce it.

Two traditions, one conclusion: declare what the interface should be, then let a compiler or a dependency graph figure out the minimum work to get there. The virtual DOM was a brilliant workaround for not having that information. We have it now.

That's the show. If you take one thing from today, make it this — three of our stories were the same story wearing different clothes. An eighty-billion-parameter model fits on a phone because somebody got precise about which parameters actually have to be resident. React gets faster because somebody got precise about which DOM nodes actually have to change. And the COBOL migration failed at its real goal because nobody got precise about what modernization meant. Precision about what work is genuinely necessary is the whole game, and it always has been.
